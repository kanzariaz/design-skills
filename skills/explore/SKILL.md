# explore — think out loud without committing anything

The user often has a /list-it list running (decided work, queued) and wants to
kick an idea around WITHOUT it landing on that list. /explore is the sandbox
lane; the list is the conveyor belt. They run in parallel and never leak into
each other.

## While exploring

1. Treat the topic as undecided by definition. Offer options, trade-offs,
   references, quick /mock-it rounds, napkin math — whatever moves the idea.
   Push back honestly; exploration is where disagreement is cheapest.
2. Do NOT: add anything to the /list-it list, edit code, or create durable
   records. Reading code/data to inform the exploration is fine.
3. If a running list exists, leave it exactly as it stands — restate it only
   if the user asks. Interleaving is expected: an /explore round can happen
   between two /list-it item additions.
4. Keep each exploration scoped to its topic; if the user opens a second
   thread, name them when summarizing so nothing blurs.

## Leaving exploration

**"Execute" is the verb that ends exploring.** Until the user says "execute"
(or an unmistakable equivalent), stay in exploring mode — even after a
direction is picked, a plan is approved, or the user sounds enthusiastic
("let's do that", "let's start with A" = a pick, NOT permission to build).
A pick narrows the exploration; only "execute" converts it into real work.

An exploration ends one of three ways — always confirm which:
- **Picked** → the user states a direction; offer the one-liner for /list-it
  (or for the project's deferred-work tracker if it's for later) and add it
  only on their word.
- **Parked** → worth keeping, not now: record it wherever the project keeps
  deferred work (a backlog file, an issue tracker, a parked list), with the
  exploration's artifacts/mockups linked.
- **Dropped** → note the dead end in one line (dead ends are findings too),
  nothing recorded unless the user wants it.
